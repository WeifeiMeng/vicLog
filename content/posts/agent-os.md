“AgentOS”常被用来描述智能体时代的操作系统，但目前它并不是像 POSIX 那样有统一规范的产品类别。更准确地说，它是一种架构视角：当大量 Agent 需要长期运行、共享工具和资源时，我们需要一个类似操作系统的基础层来管理它们。

## 为什么会出现 OS 类比

单次模型调用像执行一个纯函数；Agent 却更像进程：它有目标、状态、上下文、权限和生命周期，会等待外部事件，也可能崩溃、恢复或派生子任务。

传统操作系统管理 CPU、内存、文件和进程，AgentOS 管理的则是模型调用额度、上下文窗口、工具、记忆、凭证、沙箱和任务。两者都在解决同一个问题：让多个不完全可信的执行单元安全、有效地共享有限资源。

## AgentOS 的核心组件

### Runtime：执行与生命周期

Runtime 驱动 Agent Loop，维护任务状态，处理暂停、恢复、取消、超时和重试。模型供应商可以替换，但运行状态不能因此丢失。

### Context Manager：认知内存

它从历史、记忆、检索结果和环境状态中选择信息，控制 Token Budget，并在上下文过长时压缩。MemGPT 将这种机制类比为虚拟内存：在有限的快速空间和更大的外部存储之间移动数据。

### Tool System：设备与系统调用

工具连接文件系统、浏览器、数据库和业务 API。工具注册表描述能力，权限系统决定某次任务是否可用，执行器负责参数验证、隔离、超时和审计。

### Sandbox：隔离与最小权限

代码执行、文件修改和网络访问都需要边界。不同任务应使用独立工作区和凭证，危险操作需要提升权限或人工确认。沙箱不是附加功能，而是自主性的前提。

### Scheduler：任务与资源调度

调度器决定哪些任务并发、哪些等待依赖、如何分配模型和预算。多 Agent 协作还需要消息传递、结果汇总和冲突处理。

### Observability：事件日志与评估

系统要记录每轮模型请求、工具调用、状态变化、成本和错误。日志不仅用于排障，也是重放、评估和改进 Agent 的基础。

## 一个请求如何流经 AgentOS

```text
用户目标
  → 创建 Run 与权限上下文
  → 装配模型上下文
  → 模型选择行动
  → 工具在沙箱中执行
  → 结果写入事件日志与记忆
  → 调度下一轮或结束
```

每一层都应有清楚的契约。模型输出不是事实，工具成功不等于目标完成，记忆写入也不能先于主任务成功。

## AgentOS 真正的价值

它不是给 Agent 加一层宏大的名字，而是把散落在应用代码里的共性问题沉淀下来：身份、权限、状态、资源、隔离、调度和可观测性。未来模型会持续变化，但这些系统问题不会消失。

如果说模型是 Agent 的“大脑”，AgentOS 更像神经系统与生存环境：它让智能拥有可以持续、安全行动的身体。
