当一个任务包含调研、实现、测试和审查时，很自然会想到让多个 Agent 分工。但“多开几个模型实例”并不会自动产生团队能力。如果职责重叠、共享状态混乱、没有验收机制，得到的只会是更昂贵的重复劳动。

## 为什么需要多个 Agent

单 Agent 的主要瓶颈不只是模型能力，还有上下文容量和注意力分散。一个 Agent 同时阅读整个仓库、维护需求、写代码和自我审查，很容易在长链路中丢失约束。

多 Agent 可以把问题拆成相对独立的工作单元：研究者收集事实，实现者修改代码，测试者构造验证，审查者检查风险。每个角色拥有更小、更聚焦的上下文，也更容易定义完成条件。

## 三种常见组织方式

**中心编排**由一个 Orchestrator 拆任务、分配工作并汇总结果。它容易控制预算和依赖，适合大多数工程任务，但中心节点会成为信息和决策瓶颈。

**流水线**让输出按顺序传递，例如需求分析 → 实现 → 测试 → 审查。流程可预测，却不适合依赖频繁变化的探索任务。

**对等协作**允许 Agent 彼此通信、协商和竞争，灵活性最高，但更容易出现消息爆炸、责任不清和循环讨论。

实际系统常采用混合方式：由中心编排总体依赖，对相互独立的任务并行处理，在关键节点设置确定性的验收门。

## 任务契约比角色名称更重要

“你是资深工程师”并不能构成可靠分工。一个好的委派至少应包含：目标、允许访问的资源、不可改变的约束、期望产物、验收命令，以及遇到阻塞时如何报告。

子 Agent 返回的也不应只有“完成了”。编排器需要得到事实：改了哪些文件、运行了什么验证、有哪些假设、还剩什么风险。没有结构化交付，汇总者只能重新做一遍调查。

## 共享状态应该尽量少

多个 Agent 同时修改同一文件会产生冲突，也让错误难以归因。更稳妥的做法是按目录、模块或任务划定所有权；需要共享的事实通过明确的消息或不可变产物传递。

并行也不是越多越好。只有当任务彼此独立、不会竞争同一资源时，并行才真正缩短时间。存在依赖的工作应该串行：先确定接口，再分别实现消费者和提供者。

## 谁来判断完成

多智能体系统必须把生成与验证分开。实现者可以运行测试，但最终编排器仍应独立检查差异和验收结果。对于主观任务，可以使用评审 Agent；对于编译、测试和安全策略，应优先使用确定性工具。

多 Agent 的本质不是“群聊”，而是分布式工作系统：任务需要可分解，状态需要可追踪，结果需要可合并，失败需要可恢复。只有把这些工程问题解决，模型数量才会真正转化为协作能力。
