Prompt Engineering 关注“这句话应该怎么写”，Context Engineering 关注“模型在这一刻应该看到什么”。对于简单问答，两者差别不大；对于需要多轮执行的 Agent，后者才是决定稳定性的系统工程。

## 上下文不只是 System Prompt

一次模型调用可能同时包含：系统规则、用户目标、历史消息、用户画像、检索材料、工具定义、工具结果、当前计划、环境状态和输出格式。它们来自不同模块，却共同竞争有限的上下文窗口。

因此真正的链路是：

```text
多种信息源 → 选择与排序 → 权限过滤 → 压缩与渲染 → 模型请求
```

如果这条链路不可观察，开发者就会反复修改 Prompt，却不知道关键资料其实根本没有被加载，或已在压缩时被删除。

## 相关不等于应该注入

信息进入上下文至少要满足四个条件：与当前目标相关、来源可信、用户有权访问、在当前时点仍然有效。语义相似度只能解决第一项的一部分。

例如用户问“这个服务为什么启动失败”，相似度检索可能召回旧版本的部署文档；但当前分支的配置和最新日志优先级更高。上下文装配需要显式处理时间、作用域和事实来源。

## Token Budget 是资源调度

窗口再大也不意味着应该塞满。过长输入增加延迟和成本，还可能让关键证据淹没在中间位置。更合理的做法是为不同信息分配预算：核心规则始终保留，最近执行结果优先，长日志按需截取，历史决策压缩后保留引用。

压缩必须可追溯。摘要负责提供导航，原始事件仍保存在外部存储中；当细节影响决策时，Agent 可以重新读取，而不是把摘要当作唯一真相。

## 上下文还需要隔离

不同任务、用户和 Agent 不应默认共享全部记忆。多租户系统必须在检索之前应用权限边界；子 Agent 只获得完成任务需要的最小信息；工具返回的网页和文件内容应被视为数据，而不是可以覆盖系统规则的指令。

这也是抵抗 Prompt Injection 的关键：安全不能依赖一句“忽略恶意内容”，而要通过信息来源标记、工具权限和执行确认限制不可信文本的影响范围。

## 如何评价上下文工程

可以记录每次请求中各类信息占用的 Token、召回来源、压缩前后大小以及最终是否被模型引用。再用一组真实任务检查：关键事实是否出现、错误信息是否混入、上下文变化是否导致行为漂移。

Prompt 是上下文的一部分，但 Context Engineering 管理的是整个认知工作台。它决定模型得到怎样的世界切片，也决定 Agent 能否在长任务中持续保持方向。
