Agent 的核心不是某段神秘 Prompt，而是一个持续运行的闭环。模型每次只决定有限的一步，系统执行这一步，再把真实结果反馈回来。多个回合连接起来，才形成一次可验证的任务执行。

## 基本循环

最小的 Agent Loop 可以写成：

```text
while 未完成且未超出预算:
    observation = 读取当前状态
    decision = 模型决定下一步
    result = 执行工具或输出答案
    state = 记录结果并更新上下文
```

这对应 `Observe → Plan → Act → Reflect`。ReAct 工作展示了推理与行动交替的价值：推理帮助模型维护计划，行动则从外部环境带回新信息，防止整个过程只在模型内部猜测。

## 一次工具调用发生了什么

假设模型决定读取配置文件。生产级 Runtime 不会直接执行一段自然语言，而是要求模型输出结构化调用：工具名、参数和调用标识。随后系统依次完成：

1. 检查工具是否在当前任务中可用；
2. 校验参数是否符合 Schema；
3. 应用权限、路径和资源限制；
4. 执行并捕获标准输出、错误与超时；
5. 将结果转换为模型能够理解的消息；
6. 把事件写入日志，进入下一轮决策。

工具返回“成功”不代表目标已完成。Agent 还应检查结果是否满足验收条件。例如修改代码后必须重新运行测试，而不能只根据补丁看起来合理就宣布结束。

## 计划不是一次性生成的

长任务开始时可以先产生高层计划，但计划必须允许修正。工具可能失败，仓库状态可能与预期不同，用户也可能在执行中追加约束。有效的计划更像导航路线：目标相对稳定，下一段路径根据当前位置重新计算。

因此系统通常同时维护三种状态：不可随意改变的用户目标、可以调整的工作计划，以及每一步已经发生的事实。把三者混为一谈，Agent 就容易把自己的推测当作真实状态。

## 失败、重试与恢复

不是所有失败都应该重试。网络超时可以采用有限次数的退避重试；参数错误应当先修正输入；权限不足需要请求授权；测试失败则应回到诊断阶段。盲目重复同一个动作只会消耗 Token 和外部资源。

每个有副作用的工具还要考虑幂等性。创建订单、发送消息、删除资源等操作如果因超时而无法确认结果，直接重试可能造成重复执行。Runtime 应保存调用标识或先查询外部状态，再决定是否继续。

## 什么时候停止

Agent 至少有四类终止条件：目标已通过验收、需要用户输入、达到时间或成本预算，以及检测到无法安全继续。最后一种尤其重要——可靠的自主系统不以“永不放弃”为目标，而以“知道什么时候应该停下来”为能力。

一个成熟的 Agent Loop，本质上是把不确定的模型决策放进确定的工程护栏中。模型负责提出下一步，系统负责验证这一步是否允许、是否执行成功，以及是否真的更接近目标。
